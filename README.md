By [Simon Hampel](mailto:simon@hampelgroup.com)

A [PHPStan](https://phpstan.org) extension for add-ons developed inside a XenForo 2 install. It
carries what every add-on would otherwise have to work out alone: the configuration that lets
PHPStan see the forum without analysing it, the legacy class names XenForo 2.3 aliases at runtime,
the `XFCP_` parent of every class extension, the methods those extensions add to core classes, and
the container shortcuts given the short `Vendor\AddOn:Name` identifier.

**Without it, PHPStan reports a working add-on as broken.** On a real add-on the count at level 2
went from 262 errors to 12 on configuration alone, and from 12 to 2 once the extensions were in
place; across seven add-ons the residual fell by between a quarter and six sevenths. What is left is
real.

## Installation

In the add-on's directory:

```bash
composer require --dev hampel/xenforo-phpstan
vendor/bin/xenforo-phpstan generate
```

`generate` reads the forum the add-on sits in and writes three files into
`<forum>/internal_data/phpstan/`: a stub declaring every legacy class name the forum aliases, a
stub declaring the `XFCP_` parent of every class extension the install has, and the map the
extensions read. **Run it again after upgrading XenForo or changing a class extension** — a stale
set fails loudly, naming the two versions and this command.

**The `^0.x` constraint Composer writes is deliberate, and a new minor is a deliberate move.**
Below 1.0 a caret pins the minor, so `^0.4` means `>=0.4 <0.5`: a patch release arrives with
`composer update`, and a minor does not. Each minor so far has changed what an add-on sees at its
level, such as a bare `Tree` becoming a missing-generics report, so a minor is taken on purpose,
by naming the new minor in the constraint, and read against the changelog, whose entry for each
minor carries the `composer require` line. If `composer update` reports nothing to do after a
release, that is the constraint, not Packagist.

The forum is found four directories above the working directory, which is where it is from an
add-on at `src/addons/<Vendor>/<AddOn>`. From anywhere else, name it:

```bash
vendor/bin/xenforo-phpstan generate --root=/path/to/forum
```

The set is shared by every add-on on the forum, so before regenerating it under someone else's
analysis, ask whether it is still current:

```bash
vendor/bin/xenforo-phpstan generate --check
```

It writes nothing and applies the test PHPStan applies on first use: exit 0 and the generated
date when the set is current, exit 1 and the reason when it is missing, stale or written by an
older release.

## Configuration

The add-on's own `phpstan.neon` includes the fragment and supplies what is the add-on's: its paths,
its level, and the directories of its own that are not source.

```yaml
includes:
    - vendor/hampel/xenforo-phpstan/extension.neon

parameters:
    level: 2

    paths:
        - .

    excludePaths:
        # Scanned through the Composer autoloader already; scanning the directory as well lets a
        # dependency's scaffold shadow the add-on's own classes of the same name.
        analyseAndScan:
            - vendor (?)
        # Generated by XenForo, and not the add-on's code.
        analyse:
            - _output (?)
            - _releases (?)
            - _data (?)
```

The `(?)` marks a path optional. PHPStan refuses to start when an excluded path does not exist, and
an add-on that extends nothing has no `_output/`, one that has never been built has no
`_releases/`.

If the add-on uses [phpstan/extension-installer](https://github.com/phpstan/extension-installer),
the `includes` line is not needed.

### The forum root

`extension.neon` takes the forum to be four directories above where PHPStan runs. To analyse an
add-on from somewhere else — a checkout outside the install, a CI job with a forum unpacked
beside it — set the root, and if the generated files are elsewhere, that too:

```yaml
parameters:
    xenforo:
        root: /path/to/forum
        generated: /path/to/forum/internal_data/phpstan
```

### Magic properties

Entity columns, options and route parameters are magic properties, and PHPStan reports each
access as undefined. The add-on object's are typed individually, as the next section describes;
these three classes have no static answer, and `crates.neon` opts them into PHPStan's
object-crate treatment:

```yaml
includes:
    - vendor/hampel/xenforo-phpstan/extension.neon
    - vendor/hampel/xenforo-phpstan/crates.neon
```

**It is a separate file because the cost is real: a crate accepts any property name, so a
mistyped column is silenced as readily as a correct one.** The precise alternative for entities is
`php cmd.php xf-dev:entity-class-properties`, which writes `@property` docblocks into the add-on's
own entity classes — an edit to committed source, so a decision for each add-on rather than a
default. An add-on with no entity of its own usually needs neither: XenForo's own entities carry
`@property` docblocks, so `$visitor->user_id` is already typed, and a crate would only hide a
mistyped name.

The three classes need not go together. Route parameters have no static type anywhere, while
entity columns have one wherever a `@property` docblock exists, so an add-on that wants
`$params->user_id` quiet without crating every entity lists the one class itself instead of
including the file:

```yaml
parameters:
    universalObjectCratesClasses:
        - XF\Mvc\ParameterBag
```

A crate also decides what a class extension's added columns look like, and the answer depends on
the PHPStan release. The current release asks the extensions in this package before it applies
the crate, so a crated `XF\Entity\User` still types `$visitor->vendor_addon_column` from the
extension's `@property` and still reports a write to a `@property-read`; PHPStan 2.1.22 applies
the crate first, and on a crated entity every added column is `mixed` and nothing is reported.
Without crates the extension answers on both.

### A PHP floor below the analysing PHP

An add-on whose floor is below the PHP it is analysed on can have PHPStan hold it to the floor:

```yaml
parameters:
    phpVersion:
        min: 70400
        max: 80500
```

**That reports syntax newer than the floor, and nothing else.** A `match`, a union type, a
nullsafe call is caught; a call to `str_contains()` on a 7.4 floor is not, because PHPStan reads
functions from the PHP it runs on. It also applies to everything analysed, and PHPUnit 12 is not
readable as 7.4 code, so a suite under `tests/` becomes one `method.notFound` per assertion. The
shape that works is a second config for the shipped code alone, included from the first:

```yaml
# phpstan.floor.neon
includes:
    - phpstan.neon

parameters:
    phpVersion:
        min: 70400
        max: 80500
    excludePaths:
        analyse:
            - tests
```

`vendor/bin/phpstan analyse -c phpstan.floor.neon` is then the floor check, and the plain run
analyses the tests. An add-on whose release build already lints on the floor PHP may decide
that is enough and leave `phpVersion` out. PHPStan's own floor is `70100`, so an add-on that
supports XenForo 2.2's PHP 7.0 holds at 7.1, which is as low as the setting goes.

### Supporting XenForo 2.2

The forum analysed against is a 2.3 install, so a guard for a 2.3 method is always true there:

```php
if (method_exists('XF', 'accessToken')) { // function.alreadyNarrowedType at level 4 and above
```

The guard is right, and the report is PHPStan being told the truth about one forum. Ignore it by
identifier and path, so a guard that stops being needed is still noticed:

```yaml
parameters:
    ignoreErrors:
        -
            identifier: function.alreadyNarrowedType
            path: Cli/Command/Validate.php
```

The same applies to `class_exists()` on a class 2.3 added, and to any branch that runs only on
2.2.

A class declared twice, inside `if (\XF::$versionId >= 2030000)` and its `else`, because 2.3 added
a return type to a method the extension overrides, is a different case: read against 2.3, the
untyped 2.2 declaration is an incompatible override, and `method.childReturnType` is one of the
reports PHPStan refuses to ignore. Excluding the file loses the 2.3 branch with it. Put the two
declarations in two files, `require`d from the one the autoloader finds by the same test, and
exclude the 2.2 file alone.

## What it does

### Scans the forum, analyses the add-on

PHPStan is told where XenForo's classes are without being asked to report on them:
`src/XF`, `src/vendor` and `src/addons` are scanned for symbols, `src/XF.php` and `src/utf8.php`
are read as files because XenForo `require()`s them rather than autoloading them, and every
add-on's `vendor/` and `_build/` are left out of the scan. The first matters more than it looks:
PHPStan consults a scanned directory before the Composer autoloader, so without it an add-on
resolves a shared dependency from whichever sibling vendored an older release of it. The second
is the copy of itself a release build makes under `_build/upload/`, which declares every class of
that add-on twice while it exists, and aborts the run if the build deletes a file as PHPStan
reads it.

### Legacy class names

XenForo 2.3 renamed its classes with type suffixes — `Tools` became `ToolsController`,
`SessionActivity` became `SessionActivityRepository` — and registered an autoloader that
`class_alias()`es each old name to the new one. PHPStan cannot follow a runtime alias, so an add-on
that extends or type-hints a legacy name sees every inherited member as undefined.

The generated stub declares each legacy name as a subclass of the renamed class. The mapping comes
from the forum itself, by asking `\XF::getAliasForClass()` for every class file under `src/XF` and
`src/addons`, so it covers all ten suffixes XenForo's table abbreviates and never invents a name
core does not alias. On 2.3.13 that is 864 declarations for core alone; 43 further aliases strip to
`Abstract`, a reserved word, and are skipped, because no source could have referenced them either.

An add-on supporting XenForo 2.2 cannot avoid this by renaming its extensions: the suffixed
classes do not exist in 2.2, and 2.2 has no alias machinery, so the legacy name is the only one
valid across the range.

### Methods and properties added by class extensions

A class extension adds methods to a core class at runtime — `Vendor\AddOn\XF\Entity\User` adds
`canUseThing()`, and every `$user` in the forum can call it. Statically every call site is typed to
`XF\Entity\User`, so PHPStan reports each such method as undefined. On a fleet of 44 add-ons this
was 396 of the 757 errors left once the configuration was right.

The reflection extension answers for those methods from the extension classes recorded at
generation time: for a call on a core class, or anything below it, it offers a method any
extension of that class declares. **The map covers every add-on installed in the forum, not only
the one being analysed**, because the methods a third-party add-on's extensions add are reachable
from any other add-on — and a packaged add-on ships without the `_output/extension_hint.php` that
would declare its `XFCP_` parents, so those are generated too, from each add-on's committed
`_data/class_extensions.xml`.

The same goes for a column or a relation an extension adds in `getStructure()`. The extension
declares it as XenForo declares its own, `@property string $vendor_addon_column` or
`@property-read Thing|null $Thing` on the class, which is what `xf-dev:entity-class-properties`
writes; inside the extension PHPStan already reads that, and through the core type, which is what
`\XF::visitor()`, a finder result or a test helper gives you, the read was `property.notFound`
from level 2. A second reflection extension offers every property the recorded extensions of a
class declare, with the declared type and writability, so `$visitor->vendor_addon_column = $x`
is typed and `$visitor->Thing = null` is reported against a `@property-read`. A property the core
class declares itself is left to PHPStan's own reading of it.

### Container shortcuts

`$this->repository('Vendor\AddOn:Name')`, `\XF::service()`, `$this->em()->find('XF:User', $id)`
and the rest are typed as `@template T` with a `class-string<T>` argument in 2.3, which the short
identifier defeats: the call returns the base type, and everything called on it is undefined. The
return type extensions expand the identifier as `\XF::stringToClass()` does, for every shortcut on
`XF`, `XF\App`, `XF\Mvc\Controller`, `XF\Mvc\Entity\Manager`, `Repository`, `Entity`,
`XF\Service\AbstractService` and `XF\Widget\AbstractWidget` — the finders, repositories,
services, entities, data classes, controller plugins, behaviours, jobs, searchers, filterers,
helpers, validators, criteria and notifiers, and a controller's `assertRecordExists()` family —
and the argument itself is no longer reported against the `class-string` annotation at level 5,
or as an unresolved template type at level 6.

Within the add-on that extends the class, the shortcut returns that extension rather than the
core class: at runtime it is what comes back, and it is the only type under which a method the
extension overrides with a different signature is called correctly. Elsewhere the core class is
returned, with every extension's added methods reachable through it. Which add-on a file belongs
to is its directory under `src/addons`, so the add-on's tests count as its own.

Passing `::class` is typed by XenForo's own annotation without any of this, and within the add-on
that extends the class it still returns the extension. It is the better form for the add-on's own
classes. It is not safe for a renamed core class while the add-on supports 2.2:
`\XF\Repository\UserRepository::class` is a string whatever is installed, and on 2.2 the class it
names does not exist.

### Undeclared return types

XenForo declares no return type on many of the methods every add-on calls: the controller's
`view()`, `redirect()`, `error()`, `message()` and `exception()`, the reply classes' parameter
getters, the finder's fluent methods, `Router::buildLink()`, `\XF::phrase()`, the database
adapter's `quote()`, `fetchAllColumn()` and `getQueryCount()`, `Entity::save()`,
`AbstractCollection::keys()`, `AbstractDdl::addColumn()`, `Request::filter()`,
`App::findByContentType()`, `NodeRepository::getFullNodeList()`, `filterViewable()` and
`mergeNodeListExtras()`, `Node::getBreadcrumbs()` and `getNodeListExtras()`,
`AddOn\Manager::getById()`, `User::canFollowUser()`, `canViewFullProfile()`,
`canViewBasicProfile()` and `hasAdminPermission()`, `Entity::getErrors()`,
`ValidateAndSavableTrait::validate()` and what it writes to `$errors`,
`MergeService::setSource()`, `setTarget()` and `merge()`, `ContinuationResult::completed()`,
the adapter's `fetchRow()`, `fetchAll()`, `fetchPairs()` and `fetchAllKeyed()`, `Structure`'s
`$columns` and `$relations`, the schema `Column`'s fluent setters, `User::hasPermission()`,
`hasContentPermission()` and `hasNodePermission()`, `AddOn::getJson()`,
`RegistrationService::_save()`, `Request::getUserAgent()` and `Templater::fnAvatar()`.
Below level 7 that costs nothing; at level 7 and above each result is `mixed`, and everything it
is passed to is reported. `stubs/core.stub` restates them with the type the method body returns,
read from 2.3.13. Three documented types are corrected rather than transcribed:
`stubs/db-schema.stub` the schema builder's `null` index name; `core.stub` the `array`
XenForo claims for `AbstractAdapter::query()`'s parameters, which core itself passes as a scalar
and the statement wraps; and the `null|StepResult` XenForo documents on `AbstractSetup`'s
`install()`, `upgrade()` and `uninstall()`, which a setup with a single step falls out of without
returning, as most do, and which PHPStan reported as a missing return in every one of them. The
stub adds `void`; only core reads the result. The finder's fluent methods are declared as
returning `static`, so a chain keeps the entity type the finder was created with, which XenForo's
own `@return Finder` on `order()` lost; the schema `Column`'s setters are declared the same way.
Two of the types are wider than an adopter asked for, because the body is: `hasPermission()` and
its two siblings return the permission's value, a bool for a flag and an int for an integer
permission such as `maxMentionedUsers`; `getUserAgent()` returns `getServer()`'s default of
`false` when the request sent no agent, which a string column set from it does not survive. Iterating a collection, or a finder, yields its entity:
`getIterator()` is restated on both, because a class declared in a stub loses XenForo's own
docblock on that one method.

The add-on object `AddOn\Manager::getById()` returns answers `$addOn->title` and
`$addOn->version_string` by magic, nine keys of its own and then any column of the installed
`XF\Entity\AddOn`. Each is typed individually, the keys from their getters and the columns from
the entity's own docblock, so a mistyped key is still reported. A key that exists only in the
add-on's `addon.json` is not offered; read it through `getJson()`. `XF\Job\JobResult` answers
`$result->completed` the same way, the one key its `__get()` has, and the stub declares it.

### Plucked columns

`$finder->pluckFrom('user_id')` replaces each fetched entity with that column, or with what a
closure returns, and XenForo declares it as returning the finder, so `fetch()->toArray()` after it
was still an array of entities. It is typed over the plucked value instead: the entity's own type
for the column, an extension's column included, the closure's return type for a closure, and
`mixed` for a column nothing declares. `fetchOne()` after `pluckFrom('username')` is
`string|null`.

### Relations by name

`$user->getRelation('Auth')` and `getRelationOrDefault('Auth')` are typed from the receiver's own
`@property-read UserAuth|null $Auth`, which every XenForo entity declares for each relation and an
extension declares for the relations it adds, through the core type as well since the properties
extension offers them there. `getRelation()` keeps the declared nullability;
`getRelationOrDefault()` creates the default, so the result is the entity itself. A name the
receiver does not declare leaves the call as XenForo left it.

### Controller actions

Every controller action returns a reply, since the dispatcher rejects anything else, and XenForo
declares none of them. An `action*` method with no return type of its own is typed
`AbstractReply`, through `$this->` and through `parent::`, so `return parent::actionIndex()` in
a controller extension is no longer `mixed`. An action that declares a return type, XenForo's or
the add-on's, keeps it.

### Request input

`$this->filter('id', 'uint')` on a controller, and `filter()` on the request, are typed from the
filter string, as `XF\InputFilterer` casts the value: `str` is a string, `uint` an int, `bool` a
bool, `num` an int or float, `datetime,obj` a `DateTime`, `array-uint` an array of int, and a
leading `?` lets null through. An array of filters is an array shape with one entry per key,
nested arrays included, so `$input['username']` is a string. A filter in a variable, or a name
the filterer does not have, leaves the call `mixed` as before.

`XF\Tree` and `XF\SubTree` are generic over the record they hold. `NodeRepository::createNodeTree()`
returns a `Tree<Node>`, a tree built by hand is typed by what it was given, and a subtree's
`record`, `children()` and `parent()` follow. That makes a bare `Tree` or `SubTree` in an add-on's
own docblock a missing-generics report at level 6 and above, as a bare `Finder` already is;
write `SubTree<Node>`.

The parameters are left as XenForo declares them, `mixed` where it declares nothing. A
parameter type is a claim about every caller, and this package types what comes back.

## Levels

**Level 2 is the place to start.** On a fleet of 44 add-ons with this configuration, the median
add-on had 8 errors at level 2, 28 of the 44 had ten or fewer, and most of what remained was the
add-on's own to fix. Level 5 is a reasonable target once the call sites are tidy; level 6 is the
missing-typehint wall. With the stubs above, level max is reachable: on one small add-on it
reports a third fewer than without them, and what remains is the add-on's own typing and
route parameters, which no static type can know.

**Above level 8, most of what is left is the add-on describing itself, not the forum.** PHPStan
never infers a return type across a method boundary, so an untyped method of the add-on's own
hands `mixed` to every caller, and each use of the result is a report. On one add-on, half of the
level-max total came from a single untyped test helper; typing the helpers answered all of it.
Before reading a residual as XenForo's, `\PHPStan\dumpType()` on the value says whose type is
missing. One residual that is neither: Symfony Console's `getOption()` and `getArgument()`
return `mixed` by Symfony's own declaration, so a CLI command narrows them itself.

## Limitations

- **A legacy name is a subclass, not an alias.** PHPStan has no notion of two names for one class,
  so a value typed to the renamed class does not satisfy a parameter typed to the legacy name. The
  shortcuts return the legacy name when the add-on used it, which keeps the add-on's own types
  consistent; a value from XenForo's own typed API may still need a docblock.
- **An overridden signature is seen only through the add-on's own shortcut.** A value that arrives
  typed as the core class from anywhere else, XenForo's own typed API included, carries the core
  signature.
- **A method reached through a base type stays undefined.** `$entity->canUseThing()` on a value
  typed `XF\Mvc\Entity\Entity` cannot be resolved by anything here, because the extension is on
  `XF\Entity\User`; that is the variable's type being too wide, and the fix is at the variable.
- **A runtime check that the add-on's own extension is applied reads as always true.** Inside the
  add-on that extends `XF\Entity\User`, `create('XF:User') instanceof Extension\User` is reported
  `instanceof.alwaysTrue`, because the shortcut returns the extension. The check is still worth
  making at runtime, where a disabled add-on or a broken extension chain would fail it; put the
  `instanceof` behind a method taking `object`, so that nothing is decided before it runs.
- **A value passed by reference inside an array literal is not tracked.** After
  `$app->fire($event, [&$collected])` PHPStan still types `$collected` as the empty array it
  started as, and every use of it is reported as unreachable or always false. That is PHPStan's
  own flow analysis, and nothing here reaches it; declare the variable's type with a docblock
  after the call.
- **Code built on another add-on's vendored library does not resolve.** Only the analysed add-on's
  `vendor/` is scanned, by design, so a class that extends a sibling add-on and calls a library
  the sibling vendors is `class.notFound`. Exclude that code from analysis; it runs in the
  sibling's context, not this add-on's.
- **A stale generated set is detected only for a XenForo upgrade.** A class extension added after
  generation is reported as an unknown `XFCP_` parent, which is loud enough; one removed is simply
  still offered. `generate --check` asks the same question and no more.
- **PHPStan resolves symbols from the project that installed it.** Run it from the add-on's own
  directory with the add-on's own `vendor/bin/phpstan`. A phar borrowed from another project
  consults that project's autoloader first, and the result quietly describes a different
  dependency tree.

## Version support

PHP 8.3, 8.4 and 8.5, and PHPStan 2.1.22 or later. The add-on being analysed can target any
XenForo 2 version; the forum it is analysed against is a 2.3 install, because the alias mapping is
asked of the forum.
