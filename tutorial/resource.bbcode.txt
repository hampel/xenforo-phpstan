A tutorial on how to use static analysis to find bugs or potential problems with your addon code - and how to set up [ICODE]hampel/xenforo-phpstan[/ICODE], an open-source composer package that helps a developer analyse XenForo addons. By the end you should have a clean run at level 2 on an add-on of your own and know what the next levels will ask of you.

[HEADING=1]What static analysis is[/HEADING]

[B]Static analysis reads your code without running it, and reports what cannot be right.[/B] Unit tests and feature tests will each run one path through your code with one set of inputs and checks one result. In contrast, an analyser reads [I]every[/I] path, with every value it can prove something about, and complains where the pieces do not fit: a method called on a value that might be null, a parameter given a string where an int is declared, a return that contradicts the docblock, a branch that can never run, a variable used before anything assigned it.

It does this from the types. PHP checks types at runtime, one call at a time, and tells you about a mismatch by throwing when it is reached. An analyser checks them all at once, before anything is reached, from the declarations and docblocks already in the code. That is why it finds the bug in the branch your tests never visited and the error page your users saw once a month.

It is not a replacement for tests. A test proves a behaviour; an analyser proves an absence of a class of mistakes. They find different things, and the second is much cheaper to add to an existing add-on, because it needs no test cases written: it reads what is there.

[HEADING=1]Why bother, for an add-on in particular[/HEADING]

An add-on is a particularly good candidate, for reasons that are specific to how XenForo works.

[LIST]
[*][B]Most of an add-on's code runs rarely.[/B] Setup steps, upgrade steps, cron entries, jobs, admin controllers, the import handler, the branch for a user with no avatar. These are exactly the paths a test suite leaves out and a manual test never reaches, and exactly where an analyser earns its keep.
[*][B]XenForo's API is large and mostly undocumented by type.[/B] A method that returns [ICODE]string|false[/ICODE] looks, in the editor, like one that returns a string. An analyser that knows the truth tells you at the call site, before a database column rejects the [ICODE]false[/ICODE].
[*][B]XenForo changes underneath you.[/B] 2.3 renamed hundreds of classes and added return types to methods you may have overridden. An analyser reads your add-on against the install it sits in and reports every override that no longer matches.
[*][B]It is cheap to run and runs everywhere.[/B] A few seconds per add-on, no database, no browser, no test fixtures. It runs in the editor, before a commit, and in CI.
[/LIST]

Some of what it has found on our own add-ons, so that this is concrete rather than hopeful:

[LIST]
[*]An import loop written as [ICODE]while ($line = trim(fgets($handle)))[/ICODE], which ends at the first blank line in the file and silently drops everything after it. It had shipped. The analyser reported a blank-line check inside the loop as always false, and it was always false because the loop condition had already stopped on exactly the line the check was waiting for.
[*][ICODE]Request::getUserAgent()[/ICODE] returns [ICODE]false[/ICODE] when the request sent no agent, and an add-on wrote it straight into a string column, so every registration from a client without a user agent failed. The analyser reported the assignment the day the return type was known.
[*]A wrong [ICODE]@return bool[/ICODE] on one method, which accounted for fifteen of the thirty-five errors the add-on had at level 5. Every caller had been treating the result as a bool, and it was not one.
[*]A test that named XenForo's [ICODE]User[/ICODE] class where the add-on's own extension of it is what comes back, so three calls in it had the wrong number of arguments. The test passed, because it never reached those lines with the arguments it would have needed.
[*]XFMG's [ICODE]MediaItem::getThumbnailUrl()[/ICODE] returns null until a thumbnail exists, and an add-on had been rendering that null as an empty [ICODE]src[/ICODE] attribute. Level 8 reports a nullable value at the place it is used, and that is where it appeared.
[/LIST]

None of these were found by a test, and none were reported by a user in terms anyone could act on.

[HEADING=1]What PHPStan does[/HEADING]

[URL='https://phpstan.org']PHPStan[/URL] is the most widely used static analyser for PHP. It is a Composer package with one command, [ICODE]vendor/bin/phpstan analyse[/ICODE], which reads a configuration file, [ICODE]phpstan.neon[/ICODE], walks the files it names, and prints a list of errors with a file, a line and a message. It changes nothing.

[B]It works in levels, from 0 to 10, and each level adds a class of check.[/B] Level 0 is the basics: unknown classes, unknown functions, wrong argument counts. Level 2 adds unknown methods and properties on every typed value. Level 5 checks the arguments you pass against the parameters declared. Level 6 asks for a type on every parameter, property and return. Level 8 reports a call on a value that might be null. Level 10, also written [ICODE]max[/ICODE], treats [ICODE]mixed[/ICODE] as the unknown it is. You choose the level in the configuration, start low, and raise it when the run is clean. A higher level never finds fewer things; it finds more of them, and asks more of your declarations in return.

PHPStan needs to see every class your code touches, but it analyses only the files you ask it to. Those are different things, and the distinction matters for an add-on. It finds classes through the Composer autoloader of the project it is installed in, and through any directories it is told to [B]scan[/B], which means read for class names without reporting on them. An add-on's classes are not in any Composer autoloader, and neither are XenForo's.

It is extensible. A PHPStan extension can tell it that a method exists where none is declared, what a call returns when the declared type is too vague, and that a particular error is not one. That is how frameworks with magic, Laravel and Doctrine among them, become analysable, and it is what the package below is.

[HEADING=1]Why a XenForo add-on needs help[/HEADING]

Run PHPStan on an add-on with nothing but a path and a level, and the first run reports several hundred errors on code that works. Every one of them is PHPStan being told less than the truth, and they come from five places.

[LIST]
[*][B]It cannot see XenForo.[/B] Nothing autoloads [ICODE]XF\Entity\User[/ICODE] from an add-on's directory, so every core class is unknown and every call on one is an error. The fix is to scan the forum's [ICODE]src/XF[/ICODE], [ICODE]src/vendor[/ICODE] and [ICODE]src/addons[/ICODE] without analysing them, which takes some care: the add-on's own [ICODE]vendor/[/ICODE] must not be scanned twice, another add-on's release build must not be read while it is being written, and two files XenForo [ICODE]require()[/ICODE]s rather than autoloads have to be named individually.
[*][B]Legacy class names are runtime aliases.[/B] XenForo 2.3 renamed its classes with type suffixes, [ICODE]XF\Repository\User[/ICODE] became [ICODE]XF\Repository\UserRepository[/ICODE], and registered an autoloader that [ICODE]class_alias()[/ICODE]es each old name to the new one when it is first used. PHPStan cannot follow a runtime alias. An add-on that extends or type-hints a legacy name, which is every add-on that supports 2.2, sees every inherited member as undefined.
[*][B]Class extensions have a parent that does not exist.[/B] [ICODE]Vendor\AddOn\XF\Entity\User extends XFCP_User[/ICODE], and [ICODE]XFCP_User[/ICODE] is a class XenForo generates in memory when it builds the extension chain. XenForo writes an [ICODE]_output/extension_hint.php[/ICODE] declaring these in development mode, but a packaged add-on ships without it, so every other add-on's extensions are unparseable from yours.
[*][B]Class extensions add methods and columns to core classes.[/B] When your [ICODE]XF\Entity\User[/ICODE] extension adds [ICODE]canUseThing()[/ICODE], every [ICODE]$user[/ICODE] in the forum can call it. Statically every one of those values is an [ICODE]XF\Entity\User[/ICODE], and the method is undefined on it. On a set of 44 add-ons this one mechanism was more than half of everything left after the configuration was right.
[*][B]Container shortcuts hide the type.[/B] [ICODE]$this->repository('Vendor\AddOn:Thing')[/ICODE] returns your repository at runtime. XenForo 2.3 types the method as returning whatever class the argument names, and the short identifier is not a class name, so the call returns the base [ICODE]Repository[/ICODE] and every method on your repository is undefined.
[/LIST]

Beyond those five there is a sixth, which costs nothing until level 7 and everything after it: [B]XenForo declares no return type on a great many of the methods every add-on calls.[/B] [ICODE]view()[/ICODE], [ICODE]redirect()[/ICODE], [ICODE]error()[/ICODE], [ICODE]buildLink()[/ICODE], [ICODE]\XF::phrase()[/ICODE], [ICODE]filter()[/ICODE], the finder's fluent methods, the database adapter's fetch methods. From level 7 each result is [ICODE]mixed[/ICODE], and everything you do with it is reported.

A single add-on could fix all of this in its own configuration, and the first few did, at the cost of a few days each and a set of files that had to be kept current by hand. It is the same work for every add-on, because every part of it is a fact about XenForo rather than about the add-on. That is what the package carries.

[HEADING=1]What the package does[/HEADING]

[URL='https://github.com/hampel/xenforo-phpstan'][ICODE]hampel/xenforo-phpstan[/ICODE][/URL] is a PHPStan extension, on Packagist, for add-ons developed inside a XenForo 2 install. It has three parts.

[B]A configuration fragment[/B] that your [ICODE]phpstan.neon[/ICODE] includes. It scans the forum without analysing it, with the exclusions above, and registers everything else here.

[B]A generator[/B] that reads the forum once and writes three files into [ICODE]internal_data/phpstan/[/ICODE]: a stub declaring every legacy class name the forum aliases, as a subclass of the renamed class; a stub declaring the [ICODE]XFCP_[/ICODE] parent of every class extension of every installed add-on; and a map of those extensions that the rest reads. It asks the forum rather than guessing from filenames, by booting XenForo's autoloader and calling [ICODE]\XF::getAliasForClass()[/ICODE] for each class file, so it never invents a name XenForo does not alias and never misses one of the ten suffixes XenForo abbreviates. It connects to nothing and executes no add-on code.

[B]Reflection and type extensions[/B] that answer the questions PHPStan cannot answer from the source. The methods, columns and relations your class extensions add are offered on the core class, with the types you declared. Every container shortcut is expanded as [ICODE]\XF::stringToClass()[/ICODE] expands it, on [ICODE]XF[/ICODE], [ICODE]XF\App[/ICODE], the controller, the entity manager, repositories, entities, services and widgets, so [ICODE]$this->repository('Vendor\AddOn:Thing')[/ICODE] is your repository. Inside the add-on that extends a class, a shortcut returns the extension rather than the core class, which is what comes back at runtime. Every controller action returns a reply. [ICODE]filter('id', 'uint')[/ICODE] is an int, [ICODE]filter('name', 'str')[/ICODE] a string, and an array of filters is an array shape. A plucked finder yields the column. A relation fetched by name is the entity the [ICODE]@property-read[/ICODE] declares.

[B]And a set of stubs[/B], docblock-only files PHPStan reads alongside the real classes, that supply the return types XenForo leaves undeclared, each read from what the method body on 2.3.13 returns. The list is long and in the README; it is what makes the higher levels reachable. Where XenForo's own docblock contradicts XenForo's own code, the stub corrects it and says so: the setup step methods a single-step setup falls out of without returning, [ICODE]noPermission()[/ICODE] taking a list, the collection filter's callback being judged on truthiness.

Three things it does not do, on purpose. It does not type a parameter beyond what XenForo declares, because a parameter type is a claim about every caller and a wrong one reports working code. It does not type a method whose result depends on data, such as a keyed [ICODE]container()[/ICODE] read or a database fetch. And it does not run any of your code or XenForo's during analysis.

[HEADING=1]Setting it up[/HEADING]

You need PHP 8.3 or later on the machine running the analysis, Composer, and an add-on that lives in a XenForo 2.3 install, at [ICODE]src/addons/<Vendor>/<AddOn>[/ICODE]. The add-on itself can support any XenForo 2 version; the forum it is analysed against is a 2.3 one, because the alias mapping is asked of the forum.

[HEADING=2]Install and generate[/HEADING]

Run the following commands [B]from the add-on's directory[/B]:

[CODE=bash]
composer require --dev hampel/xenforo-phpstan
vendor/bin/xenforo-phpstan generate
[/CODE]

The first line installs PHPStan and the package into the add-on's own [ICODE]vendor/[/ICODE], which is where PHPStan must run from. The second finds the forum itself, which should be four directories up from where your addon is installed and writes the three generated files into the forum's [ICODE]internal_data/phpstan/[/ICODE]. It prints what it wrote: on a 2.3.13 install with a handful of add-ons that is around nine hundred legacy names and however many class extensions the install has.

The generated set belongs to the forum, not to the add-on, and every add-on on the forum shares it. [B]Run [ICODE]generate[/ICODE] again after upgrading XenForo, and after adding or removing a class extension in any add-on.[/B] A set left over from a previous XenForo version is refused rather than tolerated: PHPStan stops with one error naming both versions and the command to run. A set that predates a new class extension reports that extension's [ICODE]XFCP_[/ICODE] parent as unknown, which is loud enough. Or stop remembering altogether and run [ICODE]generate[/ICODE] in front of every analysis, as the Run section below shows. To ask whether the set is current without touching it:

[CODE=bash]
vendor/bin/xenforo-phpstan generate --check
[/CODE]

[HEADING=2]Configure[/HEADING]

Create [ICODE]phpstan.neon[/ICODE] in the add-on's directory:

[CODE=yaml]
includes:
    - vendor/hampel/xenforo-phpstan/extension.neon

parameters:
    level: 2

    paths:
        - .

    excludePaths:
        # Scanned through the Composer autoloader already; scanning the directory as well lets a
        # dependency's scaffold shadow the add-on's own classes of the same name.
        analyseAndScan:
            - vendor (?)
        # Generated by XenForo, and not the add-on's code.
        analyse:
            - _output (?)
            - _releases (?)
            - _data (?)
[/CODE]

The [ICODE](?)[/ICODE] marks a path optional. PHPStan refuses to start when an excluded path does not exist, and an add-on that extends nothing has no [ICODE]_output/[/ICODE], one that has never been built has no [ICODE]_releases/[/ICODE]. If you use [ICODE]phpstan/extension-installer[/ICODE], the [ICODE]includes[/ICODE] block is not needed.

Everything in this file is the add-on's own: its paths, its level, the directories of its that are not source. Everything that is XenForo's is in the fragment.

[HEADING=2]Run[/HEADING]

[CODE=bash]
vendor/bin/phpstan analyse
[/CODE]

From the add-on's directory, with the add-on's own [ICODE]vendor/bin/phpstan[/ICODE]. That is not fussiness: PHPStan resolves classes through the autoloader of the project that installed it, so a phar borrowed from another project, or a global install, consults that project's dependencies and quietly describes a different dependency tree. The one exception is an add-on whose checkout lives outside the install, a CI job with a forum unpacked beside it for instance, which names the forum in the configuration:

[CODE=yaml]
parameters:
    xenforo:
        root: /path/to/forum
[/CODE]

The first run is cold and takes a few seconds while PHPStan reads the forum; later runs use its cache and are quicker.

Rather than remembering to regenerate after a XenForo upgrade or a new class extension, run [ICODE]generate[/ICODE] in front of every analysis. It takes a fraction of a second (0.2 s on a forum with nine hundred legacy names and 123 class extensions), and since 0.10.7 it writes nothing when the set already there is current, so PHPStan's cache survives: PHPStan hashes every stub file and starts from scratch when one changes, which a rewritten set would have forced on every run. As a Composer script in the add-on's [ICODE]composer.json[/ICODE]:

[CODE=json]
"scripts": {
    "analyse": [
        "xenforo-phpstan generate",
        "phpstan analyse"
    ]
}
[/CODE]

Then [ICODE]composer analyse[/ICODE] is the one command, and the set is never stale when PHPStan reads it.

[HEADING=1]Reading the first run[/HEADING]

On a set of 44 add-ons with this configuration, the median add-on had 8 errors at level 2, and 28 of the 44 had ten or fewer. What is left is nearly always real, or at least yours, and it tends to fall into a few kinds.

[B]Magic properties.[/B] [ICODE]$user->custom_column[/ICODE], [ICODE]\XF::options()->myOption[/ICODE] and [ICODE]$params->user_id[/ICODE] are read through [ICODE]__get()[/ICODE], and PHPStan reports each as an undefined property from level 2. They are not all the same case, and the package does not paper over them with one setting:

[LIST]
[*][B]Columns of XenForo's own entities are already typed.[/B] Every core entity carries a [ICODE]@property[/ICODE] docblock for each column and relation, so [ICODE]$visitor->user_id[/ICODE] is an int without anything from you.
[*][B]Columns your extension adds to a core entity are typed from your extension's docblock.[/B] Declare them as XenForo declares its own, [ICODE]@property string $vendor_addon_column[/ICODE] on the extension class, which is what [ICODE]php cmd.php xf-dev:entity-class-properties[/ICODE] writes, and they are typed through the core class too, from [ICODE]\XF::visitor()[/ICODE] or a finder result.
[*][B]Columns of your own entities want the same docblock.[/B] Run [ICODE]xf-dev:entity-class-properties[/ICODE] and commit the result. It is an edit to source, so a decision, but it is the precise answer.
[*][B]Your own options are typed by listing XenForo's option hint as a stub.[/B] Development mode writes [ICODE]_output/option_hint.php[/ICODE] for every add-on; [ICODE]stubFiles: [_output/option_hint.php][/ICODE] in the parameters types every option of yours and still reports a misspelt one. Core options can be typed the same way with [ICODE]xf-dev:generate-options-stub[/ICODE]; the README has the recipe, and one trap in it.
[*][B]Route parameters have no static type anywhere.[/B] [ICODE]$params->user_id[/ICODE] is whatever the route format said, and the honest answer is the crate: listing [ICODE]XF\Mvc\ParameterBag[/ICODE] under [ICODE]universalObjectCratesClasses[/ICODE] tells PHPStan the class answers any property name. The package ships a [ICODE]crates.neon[/ICODE] that does this for entities, options and parameters together, and says in the README why it is a separate file: a crate silences a mistyped name as readily as a correct one, so take it per class, and only where nothing more precise exists.
[/LIST]

[B]A value typed too widely.[/B] [ICODE]$entity->canUseThing()[/ICODE] on a value typed [ICODE]XF\Mvc\Entity\Entity[/ICODE] is undefined, and nothing can make it otherwise, because your extension is on [ICODE]XF\Entity\User[/ICODE]. That is the variable's type being too wide, and the fix is at the variable, usually a docblock on a parameter. The same goes for a [ICODE]@return Entity[/ICODE] on your own method that returns a user.

[B]A check that is now always true.[/B] Inside the add-on that extends [ICODE]XF\Entity\User[/ICODE], the shortcut returns your extension, so [ICODE]create('XF:User') instanceof Extension\User[/ICODE] reads as always true. The check is still worth making at runtime, where a disabled add-on would fail it; put the [ICODE]instanceof[/ICODE] behind a method that takes [ICODE]object[/ICODE], so nothing is decided before it runs. A guard for a 2.3 method, [ICODE]method_exists('XF', 'accessToken')[/ICODE], is always true against a 2.3 forum for the same reason, and the section on 2.2 below says what to do with it.

[B]Something wrong.[/B] The rest. Read each one as if a careful colleague had written it in a review, because that is roughly what it is.

When a report is puzzling, ask PHPStan what it thinks the value is:

[CODE=php]
\PHPStan\dumpType($value);
[/CODE]

It reports the type as an error on that line, and the type tells you whose declaration is missing: yours, XenForo's, or a dependency's.

[HEADING=1]Climbing the levels[/HEADING]

[B]Level 2 is the place to start, and a clean level 2 is worth committing before going further.[/B] Raise the level one step at a time, and at each step decide for each new report whether to fix it or to ignore it with a reason.

Ignore by identifier and path, never by message alone and never globally:

[CODE=yaml]
parameters:
    ignoreErrors:
        -
            identifier: function.alreadyNarrowedType
            path: Cli/Command/Validate.php
[/CODE]

PHPStan reports an ignore that no longer matches anything, so a guard that stops being needed is still noticed. The identifier is printed under each message in the default output.

For an add-on with hundreds of reports at the level you want, PHPStan's baseline records all of them in a file so that only new ones are reported:

[CODE=bash]
vendor/bin/phpstan analyse --generate-baseline
[/CODE]

That is a debt register rather than a fix. It lets a large add-on start at a useful level today and pay the list down over time, and it is the right move for an add-on nobody is going to spend a week on first.

What each level asks for, in the order you will meet them:

[LIST]
[*][B]Level 5[/B] checks arguments against parameters. The most common report here on an add-on is a nullable value passed where the parameter is not nullable, and most of those are real.
[*][B]Level 6[/B] asks for a type on every parameter, property and return. This is the wall, and on an add-on it is mostly your own methods. On a class other add-ons extend, which is any class you register through [ICODE]extendClass()[/ICODE] and any you expect to be subclassed, do not add a native return type: an override written without it, as every existing one was, becomes an incompatible declaration PHP refuses to load. Type those by docblock, which PHPStan reads the same way. A bare [ICODE]Finder[/ICODE], [ICODE]Tree[/ICODE] or [ICODE]SubTree[/ICODE] in a docblock is reported here as missing its generic type; write [ICODE]Finder<Thing>[/ICODE].
[*][B]Level 7[/B] is where an undeclared return type starts to cost, and where the stubs do their work. Without them, every [ICODE]view()[/ICODE], [ICODE]redirect()[/ICODE] and [ICODE]fetch()[/ICODE] is [ICODE]mixed[/ICODE] from here.
[*][B]Level 8[/B] reports a call on a value that might be null, at the place it is used. This is the level that found the thumbnail URL, and it finds something in most add-ons.
[*][B]Level 9 and 10[/B] treat [ICODE]mixed[/ICODE] as the unknown it is. Above level 8, most of what is left is the add-on describing itself rather than the forum: PHPStan never infers a return type across a method boundary, so an untyped method of your own hands [ICODE]mixed[/ICODE] to every caller. On one add-on, half of the level-max total came from a single untyped test helper. What remains once your own methods are typed is a core method the stubs do not yet cover, which is exactly the kind of report the package wants to hear about, and the route parameters, which no static type can know.
[/LIST]

Several of our add-ons are clean at level max with no baseline and no ignores. It is reachable, and the climb from 2 to max on a small add-on is an afternoon.

[HEADING=2]Where to stop[/HEADING]

[B]Nothing requires you to reach max, and for some add-ons the last few levels are a lot of work for no tangible gain.[/B] The levels do not all pay the same, and the right place to stop depends on the add-on and on how often you will touch it again.

Two levels find bugs on their own. Level 5 checks every argument against its parameter, and most of what it reports on an add-on is real. Level 8 reports a call on a value that might be null, and finds something in most add-ons. Between them, level 6 finds very little and costs the most, because it asks for declarations rather than checking behaviour: one add-on went from 3 reports at level 5 to 67 at 6, another from a clean 5 to 239, a third from 16 to around 600, and almost none of those were defects. Above 8, the reports are about your own declarations rather than your code's behaviour. So [B]a reasonable aim is level 5 for anything you ship, level 8 for anything you maintain actively, and max when the add-on is small or new enough that typing everything is an afternoon rather than a week[/B].

The ongoing cost matters as much as the climb. A higher level is more friction on every future change, because each new method has to be fully declared before the run is clean, and each new release of this package can move the count at level 7 and above as a type is added or corrected. A large add-on nobody is going to spend a week on is better at a clean level 5 it can hold than at a level max it holds only through a baseline. Where you do want a higher level on an add-on like that, the baseline is the honest tool: set the level you want new code held to, record what exists, and pay the list down when you are in that file anyway.

[HEADING=1]Supporting XenForo 2.2[/HEADING]

An add-on that supports 2.2 is analysed against a 2.3 forum, and three things follow.

[B]Keep the legacy class names.[/B] The suffixed classes do not exist in 2.2, and 2.2 has no alias machinery, so [ICODE]XF\Repository\User[/ICODE] is the only name valid across the range. The generated stub makes it analysable. For the same reason, [ICODE]::class[/ICODE] on a renamed core class is not safe while 2.2 is supported: [ICODE]\XF\Repository\UserRepository::class[/ICODE] is a string whatever is installed, and on 2.2 the class it names does not exist.

[B]Hold PHPStan to your PHP floor.[/B] [ICODE]phpVersion: {min: 70400, max: 80500}[/ICODE] reports syntax newer than the floor, a [ICODE]match[/ICODE] or a nullsafe call, and nothing else: a call to [ICODE]str_contains()[/ICODE] on a 7.4 floor is not caught, because PHPStan reads functions from the PHP it runs on. It also makes PHPUnit 12 unreadable, so the shape that works is a second configuration for the shipped code alone, included from the first, with [ICODE]tests[/ICODE] excluded. The README has it. PHPStan's own floor is 7.1, so an add-on supporting 2.2's PHP 7.0 holds at 7.1.

[B]Expect the version guards to read as always true.[/B] [ICODE]method_exists()[/ICODE] and [ICODE]class_exists()[/ICODE] checks for things 2.3 added are PHPStan being told the truth about one forum. Ignore each by identifier and path, as above, so a guard that stops being needed is still noticed.

[HEADING=1]Running it in CI[/HEADING]

The one thing a CI job cannot download is XenForo, so a job needs a forum unpacked beside the checkout, from your own copy, and [ICODE]xenforo.root[/ICODE] pointing at it. The generated set can be produced in the job with [ICODE]generate --root=[/ICODE], since the generator needs nothing but the files. Everything else is the same [ICODE]vendor/bin/phpstan analyse[/ICODE].

Short of that, a pre-commit hook that runs the analysis from the add-on's directory catches most of what CI would, and costs a few seconds.

[HEADING=1]What it will not do[/HEADING]

[LIST]
[*][B]A legacy name is a subclass, not an alias.[/B] PHPStan has no notion of two names for one class, so a value typed to the renamed class does not satisfy a parameter typed to the legacy name. The shortcuts return the legacy name when the add-on used it, which keeps your own types consistent; a value from XenForo's own typed API may still need a docblock.
[*][B]An overridden signature is seen only through your own shortcut.[/B] A value that arrives typed as the core class from anywhere else carries the core signature.
[*][B]Code built on another add-on's vendored library does not resolve.[/B] Only the analysed add-on's [ICODE]vendor/[/ICODE] is scanned. Exclude that code; it runs in the sibling's context.
[*][B]A value passed by reference inside an array literal is not tracked.[/B] After [ICODE]$app->fire($event, [&$collected])[/ICODE], PHPStan still types [ICODE]$collected[/ICODE] as the empty array it started as. That is PHPStan's own flow analysis; declare the type with a docblock after the call.
[*][B]It does not know what a route parameter, a keyed container entry or an option holds[/B], beyond what a stub or a docblock of yours says. Those are facts about an install.
[/LIST]

The README is the reference, and it goes into more detail than this on every section above: the options recipes, the floor configuration, the full list of typed methods and corrected docblocks, and the limitations.

The list of return types the stubs carry has grown almost entirely from reports: an add-on reaches level 9, finds a core method that comes back [ICODE]mixed[/ICODE], and says so. If you reach a core method the package does not yet type, or a report you think is wrong, open an issue with the method, the level and what PHPStan printed. A [ICODE]\PHPStan\dumpType()[/ICODE] on the value is the most useful single line to include.
